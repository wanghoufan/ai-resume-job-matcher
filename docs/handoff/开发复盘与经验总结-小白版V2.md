## 2. 当前能力

### 岗位匹配 1.0

- 登录后上传 PDF、粘贴 JD，使用四家白名单厂商的 BYOK 模型。
- 输出匹配度、建议、求职信、面试问答和雷达图。
- Supabase 保存私有简历、JD 和最近 30 条分析历史。

### 在线简历 2.0

- `/resume-sites/new`：PDF 拖放/点击上传，或选择本人历史分析；四主题；BYOK 生成。
- `/resume-sites/{id}/edit`：编辑结构化内容、自动保存、revision 乐观锁、主题和手机预览。
- `/r/{slug}`：无需登录的公开页。
- 发布使用独立 `resume_site_publications` 快照；取消发布只关闭快照，不删除草稿。
- 未选择公开的联系方式会从公开 JSON 中删除，不是 CSS 隐藏。

详细产品合同和验收标准见 `docs/pm/PLAN.md`。

## 3. 关键架构边界

1. 私有草稿 `resume_sites` 与公开快照 `resume_site_publications` 必须分离。
2. 公开 RLS 只允许匿名读取 `is_active = true` 的快照；草稿始终按 owner 隔离。
3. AI 只生成结构化 JSON，由 `ResumeRenderer` 渲染；不接收任意 HTML。
4. `normalizeContent` 负责长度/结构标准化，`publicContent` 负责过滤隐藏联系方式。
5. BYOK key 只存在于当次请求，不进入数据库、日志、Cookie、本地存储或公开数据。
6. 模型地址维持四家服务商白名单，禁止恢复任意自定义 URL。
7. 公开页 `/r/` 跳过无意义的认证刷新，但数据读取仍受 Supabase RLS 控制。

## 8. 安全红线

- 不输出、提交或复制真实 API Key、OAuth 凭据和 `.env.local` 内容。
- 不在浏览器暴露 `service_role`/secret key。
- 私有 Storage bucket 和所有业务表必须维持 RLS。
- 修改公开数据模型时同步检查 `publicContent`、RLS、GRANT 和匿名访问回归。
- 删除简历必须同时删除私有 Storage 原文件；取消发布不等于删除草稿。
- 服务端错误先脱敏再返回，日志不得包含 BYOK key。
